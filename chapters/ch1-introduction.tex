\section{Agentic \glsfmtshort{ai} systems and the \glsentrylong{mcp}}\label{sec:agentic-mcp}

\Gls{llm} agents no longer only generate text. Given access to external tools, they can retrieve live data, perform computations, and act on external systems~\cite[p.~2]{Hou2026}. This access broadens what an agent can do and expands what can go wrong. \textcite{Ruan2024} observe that tool use amplifies risks such as unwanted disclosure of private data, financial ruin, or even physical injuries in the case of autonomously operated robots~\cite[p.~1]{Ruan2024}. Across 144 test cases in their emulated sandbox, even the safest agent they tested failed with potentially severe outcomes 23.9\% of the time, according to their automatic evaluator~\cite[p.~2]{Ruan2024}.

Until recently, connecting an agent to a tool meant integrating each service separately. Developers had to define the \gls{api}, authentication, and execution logic of each service, while function-calling mechanisms differed between \gls{ai} models and harnesses~\cite[p.~2]{Hou2026}. The \gls{mcp}, launched by Anthropic in late 2024, standardises how \gls{ai} applications define, discover, and invoke external tools~\cite[p.~2]{Hou2026}. The \gls{ai} application acts as an \gls{mcp} client and communicates with \gls{mcp} servers, which give it a unified interface for tool access~\cite[p.~4]{Hou2026}.

Adoption of this protocol has been rapid. \textcite{Hou2026} describe integrations by OpenAI, Cursor and Cloudflare, and catalogues 26 major community-driven \gls{mcp} collections, among them websites, GitHub repositories, and desktop applications, several of which host thousands of servers~\cite[pp.~11--13]{Hou2026}. A National Security Agency advisory calls \gls{mcp} \enquote{the de facto standard} for communication between \gls{ai}-driven services, and warns that its rapid adoption has far surpassed the state of its security model~\cite[p.~1]{NSA2026}. \Gls{mcp} has therefore made it routine for an agent to rely on a server that a third party wrote and maintains.

\section{Problems with trusting \glsfmtshort{mcp} servers}\label{sec:untrusted-server}

An \gls{mcp} server is trusted twice, once by the model that uses it and once by the user who installs it, and neither check is reliable. \textcite{Song2026} found high attack success rates and low refusal rates when malicious servers were connected to mainstream \glspl{llm}. They describe this as \enquote{a fundamental trust paradox}: \glspl{llm} inherently trust tool outputs, which lets them complete tasks effectively, but they struggle to detect malicious intent within tool descriptions~\cite[p.~2423]{Song2026}.

The check at the time of installation is no more reliable. Most online server registries don't have adequate protections or checks against the servers they list or upload. \textcite{Song2026} uploaded malicious servers to three popular \gls{mcp} registries, and all three accepted them without resistance, applying only basic auditing. In a user study with 20 participants, they observed that participants struggled to identify malicious servers~\cite[p.~2411]{Song2026}. \textcite{Hou2026} report that MCP.so, the earliest \gls{mcp} market, lacks formal security or identity verification mechanisms, while some platforms, such as mcp-get, do verify and sign servers but host only a small number of verified ones~\cite[pp.~11--12]{Hou2026}.

The harm a malicious server can cause is well documented. \textcite{Song2026} show that attacks through malicious servers can access private files or control devices to transfer digital assets. \textcite{Greshake2023} show that \glspl{llm} capable of retrieving information are vulnerable to adversaries which can steer them by planting prompts in content retrieved at inference time~\cite[p.~80]{Greshake2023}.

This dissertation mainly focusses on a different class of threat: servers that are not malicious at first use. \textcite{Hou2026} describe this more formally as \enquote{an apparently benign MCP server, initially functioning as advertised, is later surreptitiously altered by its maintainer to introduce malicious code or terminate safe functionality}~\cite[p.~19]{Hou2026}. Rug pulls are dangerous because they introduce malicious behaviour only after building a trust relationship with users. A single compromised server can affect many users or interconnected \gls{mcp} servers at once~\cite[p.~19]{Hou2026}. The ecosystem does little to expose such a change. Aggregation platforms link to external code repositories rather than hosting the code themselves. \textcite{Song2026} found that this makes it possible for attackers to implement rug pull attacks by modifying code repositories after getting approval from the platform~\cite[p.~2415]{Song2026}. A server can therefore pass a platform's review while benign and turn malicious afterwards without being reviewed again.

Reputation research has been dealing with this pattern since before the advent of \gls{mcp}. \textcite{Hoffman2009} and \textcite{Ruohomaa2011} both discuss such attacks, and \textcite{Hoffman2009} note that attackers who follow this pattern are known as \enquote{traitors}~\cite[p.~1:13]{Hoffman2009}. However, this one-way shift differs from a cyclic attack, in which a malicious agent \textit{repeatedly regains} high trust through cooperation and then abuses it~\cite[p.~842]{Salehi-Abari2010}. In both cases, the attacker exploits a legitimately achieved high reputation.

\section{Accumulated reputation and its weakness}\label{sec:reputation}

Reputation systems judge a party by the experience of those who have dealt with it. The idea is to let users rate other service providers after an interaction and use the aggregated ratings for a particular provider to derive a trust or reputation score~\cite[p.~618]{Jsang2007}. Such systems are soft security mechanisms better suited to the case where consumers need to protect themselves from service providers and traditional access control cannot help. \textcite{Jsang2007} note their use in successful commercial online applications~\cite[pp.~618,~622]{Jsang2007}. \Gls{mcp} literature has started pointing the same way, for example \textcite{Hou2026} suggest reputation-based trust scoring for \gls{mcp} auto-installers~\cite[p.~22]{Hou2026}.

Reputation accumulated over a long history, however, has a documented weakness against the threat described in \cref{sec:untrusted-server}. When a formulation depends only on long-term history without accounting for differences in recent and old actions, an attacker with a good record can carry out short attacks with little to no risk of negative repercussions as the previous history will dominate over the recent period of actions~\cite[p.~1:13]{Hoffman2009}. However, simply giving recent evidence more weight does not remove the problem on its own. \textcite{Salehi-Abari2010} proved that malicious agents with cyclical behaviour could still exploit four trust models~\cite[p.~847]{Salehi-Abari2010}, and two of those models already weight ratings by how recent they are~\cite[p.~843]{Salehi-Abari2010}.

REV2~\cite{Kumar2018}, the rating-graph algorithm on which this dissertation builds, addresses a different weakness of simple aggregation. Its authors note that using measures like averages or median scores can be manipulated easily by creating multiple fraudulent accounts to boost or pull down provider ratings~\cite[p.~335]{Kumar2018}. REV2 therefore scores users, ratings and products jointly: \enquote{a fair user should give ratings that are close in score to the goodness of the product, and good products should get highly positive reliable ratings}~\cite[p.~333]{Kumar2018}. REV2 was evaluated on identifying fraudulent users, using the fairness scores it computes for users~\cite[p.~333]{Kumar2018}. This dissertation tests using a product's goodness score as the trust score of an \gls{mcp} server.

\section{Existing responses and research gaps}\label{sec:gap}

Two strands of work bear on this problem, and neither addresses it fully. The first is \gls{mcp} security research. In the \gls{mcp} literature reviewed here, defences examine server code or single executions. \textcite{Hou2026} recommend version pinning, having reproducible builds, and conducting cryptographic signature verification of server code, along with client-side safety measures such as update transparency and runtime monitoring to help users identify when an \gls{mcp} server started to behave maliciously~\cite[p.~19]{Hou2026}. \textcite{Huang2026} propose a detector that checks a tool's behaviour during execution against the function intent extracted from its declaration. The authors note that malicious logic not executed at runtime may evade it~\cite[pp.~1, 25]{Huang2026}. None of these defences uses evidence accumulated from clients' experience of a server over time. The timing of a rug pull is why such evidence matters: a check at approval or installation examines the server before it changes, and a check of single executions sees only the behaviour those executions exercise. This dissertation's premise is that ratings gathered from many clients over time can register harm that appears only after the server changed its behaviour, or in cases where only some clients were affected.

The second strand is the trust literature, which has several mechanisms for behaviour change, all operating on a scalar reputation value held for each trustee. Forgetting factors and sliding windows discount or discard old evidence at a rate or window length that is fixed in advance. \textcite{Player2020} describe them as limited techniques because the best window size or forgetting factor depends on the application, varies over time, and differs between agents. Moreover, the techniques are only effective for gradual change, not sudden change~\cite[p.~6]{Player2020}. Other mechanisms adapt the window itself: PeerTrust switches to a smaller time window when a peer's performance drops over a threshold~\cite[p.~849]{LiXiong2004}, but how soon it corrects the trust value depends on how small that window is~\cite[p.~854]{LiXiong2004}. A third approach is detecting the change explicitly. \textcite{Parhizkar2022} use Page--Hinkley statistics within a Beta reputation system to dismiss an agent whose behaviour worsens~\cite[p.~1]{Parhizkar2022}. However, this method can also dismiss a trustee that has turned bad yet is still the best one available~\cite[p.~11]{Parhizkar2022}.

Any mechanism that reacts to recent evidence must also decide how large a change is actionable. Giving more weight to recent negative behaviour helps with quick detection, but without proper guards the same technique also lets malicious raters prevent honest servers from building trust~\cite[p.~1:18]{Hoffman2009}. But using simple score redemption schemes allows malicious servers to disguise their attacks as temporary errors and build up reputation again quickly~\cite[p.~1178]{Chae2015}. Benign servers can also trigger a deviation-based detector: all seven false positives reported for Connor came from genuine behavioural deviations in benign servers~\cite[p.~25]{Huang2026}.

Taken together, these two strands leave a specific gap. In the literature reviewed for this dissertation, no work compares historical and recent scores from a jointly computed rating-graph model, and none calibrates such a comparison for \gls{mcp} servers. The nearest prior work is PeerTrust, which compares time windows on a scalar model~\cite{LiXiong2004}, and DGTEN, a graph-based trust model that learns temporal features to resist on-off attacks~\cite{Usman2025}.

\section{Aim and research question}\label{sec:aim}

This dissertation proposes using the REV2 algorithm as a way to compute trust scores for \gls{mcp} servers from the ratings their clients give. Its aim is to show whether computing those scores over time windows reflects a server's turn to malicious behaviour better than a single score over its whole history, so that a long record of good ratings does not mask recent low ones. To that end, it designs and evaluates a window-based mechanism that computes a server's REV2 goodness separately over a historical and a recent window of the rating graph. When the recent score has dropped below the historical score by more than a calibrated threshold, the mechanism reports the recent score in place of the historical one. Detection is judged on the trust score reported for a server. \Cref{ch:methodology} defines when a reported score counts as detecting a malicious server, and the measures used: how many malicious servers are detected, how soon after they turn malicious, and how many benign servers are wrongly flagged.

The dissertation addresses the following research question:

\begin{quote}
    To what extent does computing REV2 trust scores separately over historical and recent rating-history windows improve detection of \gls{mcp} servers that behave benignly to gain trust before exhibiting malicious behaviour, compared to computing a single REV2 trust score over the complete rating history, under simulated rating scenarios?
\end{quote}

The tension described in \cref{sec:gap}, between reacting quickly and reacting to noise, makes the threshold the mechanism's central parameter. The sub-question addresses it:

\begin{quote}
    Within the windowed mechanism, what delta threshold---the magnitude of divergence between historical and recent trust scores---best separates malicious-behaviour shifts from benign score fluctuation?
\end{quote}

\section{Scope and assumptions}\label{sec:scope}

REV2 is mapped onto \gls{mcp} as follows. Clients, or the agents acting for them, take the role of REV2's users. \gls{mcp} servers take the role of products, and a server's trust score is its goodness $G(p)$. REV2 is used in this dissertation with Laplace smoothing and fixed priors, and without its behavioural component. Windows are defined by time and cover the whole rating graph, so all three scores in a window are computed from that window's ratings alone. \Cref{ch:background} gives the configuration, and \cref{ch:literature-review} gives the reasons for it and for windowing the whole graph.

The primary threat is a one-way shift: a server that behaves benignly and then turns malicious, as in the rug pull attack scenario described in \cref{sec:untrusted-server}. Two related patterns, cyclic on-off behaviour and gradual poisoning, are treated as stress conditions rather than primary targets (\cref{ch:literature-review}).

The evaluation uses simulated rating scenarios. Simulation fixes the moment a server turns malicious, allowing for accurate calculation of detection delay. \textcite{Gama2014} support this method of evaluation, describing how periods of drifts need to be known and why synthetic data is appropriate for such assessments~\cite[p.~44:26]{Gama2014}. All of this comes at the cost of ecological validity. The results only describe how the mechanism behaves under simulated rating models, and they may not carry over directly to real rating behaviour.

Three further assumptions bound what the mechanism can do:

\begin{itemize}
  \item \textbf{Rating premise.} The dissertation assumes that a rating system is already in use, with enough active raters, in which clients rate the servers they use after interacting with them, much as buyers rate sellers on online marketplaces~\cite{Jsang2007}. How such a system is adopted, and how raters are recruited, is outside its scope. A rating records whether an interaction went right or wrong from a security point of view, as far as the user or agent could tell, not how useful the tool was. This premise does not contradict \cref{sec:untrusted-server}, which shows that neither the model nor the user reliably recognises a malicious server at the point of use or installation. A rating does not require that recognition, it needs only the consequences that some clients notice afterwards. Such ratings are partial and noisy, which is one reason REV2's weighting of raters by fairness matters here.
  \item \textbf{Observability.} The mechanism can respond only to malicious behaviour that shows up in ratings, and some attacks are designed not to. In tool poisoning, the harmful actions occur only after a seemingly correct tool has been invoked, so anomalies are likely to be attributed to model errors or benign software glitches~\cite[p.~19]{Hou2026}, and the malicious instructions in a tool description can be invisible to the user~\cite[p.~2413]{Song2026}. Behaviour disguised in this way is a limitation of the approach. The simulated scenarios therefore state how malicious behaviour becomes visible to raters.
  \item \textbf{Complementarity.} The mechanism is intended to work alongside code-level defences and execution-time detectors such as Connor~\cite{Huang2026}, not to replace them. It draws on evidence those defences do not use, i.e., the accumulated experience of a server's clients.
\end{itemize}

\section{Contributions}\label{sec:contributions}

This dissertation makes three contributions:

\begin{enumerate}
  \item \textbf{REV2 as a trust-score mechanism for \glsfmtshort{mcp} servers.} It maps clients and servers onto REV2's rater and product scores, and it analyses what windowing a coupled graph score involves.
  \item \textbf{A windowed mechanism that reacts only to drops}, together with a decision rule based on the delta between historical and recent trust.
  \item \textbf{A simulation-based evaluation against whole-history REV2} that accounts for false alarms on benign servers, with a calibration of the delta threshold and a test of how it transfers across scenarios.
\end{enumerate}
